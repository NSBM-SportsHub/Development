# Required video demonstration

The official guideline (page 4, section 4.3) requires one screen-recorded video covering login, the Admin panel, Student/User panel, CRUD, database integration, main features and a brief contribution explanation from every member. It requires an accessible video link in the report. It does not set a duration. This recording plan is preparation; no video has been recorded or uploaded by writing it.

## Recording plan

Use the [demo guide](demo-guide.md) with synthetic accounts and future-dated activities. Rehearse first, hide private configuration/credentials, and record at a readable desktop resolution. Use the mobile view briefly to show responsive behavior. Suggested timings below are a planning aid, not a lecturer-imposed limit.

| Segment | Show on screen | Suggested duration |
| --- | --- | --- |
| Introduction | Project title, team leader Mukilan Vasantharaj, purpose and stack | 20-30 seconds |
| Login and panels | Student registration/sign-in/profile; separate Admin navigation and an Admin-only route | 45-60 seconds |
| Club/membership CRUD | Admin creates/edits a club; Student applies; review/approval; refresh persistence; archival later in the recording | 60-90 seconds |
| Training and participation | Coach assignment, training schedule and attendance; Student history and Admin report totals | 60-90 seconds |
| Booking workflow | Resource creation, Student request/pending edit, Admin approval, notification and overlapping-slot rejection | 60-90 seconds |
| Competition workflow | Tournament entry/eligibility, entry review, generated fixtures, saved scores, standings and a reload | 60-90 seconds |
| Communication and retention | Published announcement/inbox; cancellation/archival retains history; logout/protected-route behavior | 45-60 seconds |
| Database evidence | Current ERD/migrations; show a synthetic stored record before/after a UI write and refresh; explain actual design changes | 45-60 seconds |
| Team contributions | Each member presents their own real code, R&D, database or UI/UX artifact and its effect on the project | About 20-40 seconds each |
| Closing | Source link, completed deliverables and application link supplied by the responsible team member | 15-20 seconds |

For database evidence, use a synthetic record in a local database viewer or a safe read-only query. Avoid displaying application keys, password hashes or session values. Show the original architecture image as the early proposal and the current 17-table ERD as the implemented schema.

## Contribution prompts

Each member should prepare their own short explanation:

1. State their confirmed name and actual responsibility.
2. Open the file, design page, diagram, research section or commit that demonstrates that contribution.
3. Explain one design or implementation choice and how it connects to the finished system.
4. Distinguish their own work from later changes by another member. Credit research and design work alongside code and QA.

The R&D header identifies Jassim and Shahilan. Use the team's confirmed credits for database architecture and UI/UX rather than inferring them solely from the original coding allocation. Each individual records their own explanation; this plan does not fabricate participation.

## Before linking the video

- Combine the demonstration and all contribution segments into one coherent recording.
- Watch the complete file; confirm readable screens, audible speech, every required topic and all members.
- Have the team upload it to the guideline's permitted accessible platform, such as an unlisted YouTube video, when ready. This document does not authorize an automatic upload.
- Test the link from a signed-out/private session and put it into the report metadata, then rebuild the PDF.
- Confirm the application link separately with the responsible team member before final submission.
